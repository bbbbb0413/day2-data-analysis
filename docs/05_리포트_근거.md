## 결정 R-1. `profile` 단계를 제거한다

**결정**
`profile` 단계를 파이프라인에서 빼고, 유일하게 겹치지 않던 **범주형 분포**만
`statistics` 단계로 옮긴다.

**근거 — 출력의 89%가 중복이다**

리포트를 처음부터 끝까지 읽어보니 같은 내용이 두세 번 나왔다.
`profile`이 내는 지표 9개 중 8개가 다른 섹션과 겹친다.

| `profile` 지표 | 중복 대상 |
|---|---|
| `describe` | 통계분석 §기술통계 |
| `correlation` | 통계분석 §상관계수 |
| `mean_over_median` | 차트 1 (수치형 분포) |
| `by_hour` | 차트 3 (시간대별 패턴) |
| `by_dayofweek` | 차트 4 (요일별 패턴) |
| `by_distance_bucket` | 차트 5 (거리-요금 관계) |
| `by_record_source` | 차트 7 (소스별 프로파일) |
| `top_pickup_zones` | 차트 10 (존 TOP 20) |
| **`categorical_full_only`** | **겹치지 않음** |

`profile`은 시각화·통계 단계를 만들기 전에 작성한 것이라 그때는 유일한
EDA 출력이었다. 이후 차트와 통계표가 같은 내용을 더 잘 보여주게 되면서
역할이 사라졌다.

**반례 — 그대로 두면**
리포트에서 시간대별 운행량을 세 번 보게 된다. 차트 3(그림), 기본 EDA
막대(텍스트), 그리고 차트 8 히트맵(다른 축). 읽는 사람은 "왜 같은 걸
반복하지?"라고 생각하며 신뢰를 잃는다. 리포트 313줄 중 약 60줄이 중복이었다.

**기본 EDA 내용은 빠지지 않는다**
기술통계·상관계수는 `statistics`가, 분포·그룹 비교는 차트 10개가 담당한다.
범주형 분포만 `statistics`로 옮기면 빠지는 내용이 없다.

**한계**
단계를 지우면 `metrics.json`에서 `profile` 키가 사라져, 과거 실행과
비교할 때 키가 맞지 않는다. 다만 같은 지표가 다른 키(`statistics`,
`visualize`)에 남아 있어 실질적 손실은 없다.

## 결정 R-2. 리포트 순서를 읽는 사람의 질문 순서로 배치한다

**결정**

| 순서 | 섹션 | 답하는 질문 |
|---|---|---|
| 1 | 개요 | 무엇을 한 분석인가? |
| 2 | 실행 정보 | 어떤 데이터·기준으로 돌렸나? |
| 3 | 품질 게이트 | **이 결과를 믿어도 되나?** |
| 4 | 데이터 준비 | 원본을 어떻게 다듬었나? 왜 그렇게 했나? |
| 5 | 시각화 | 데이터가 실제로 어떻게 생겼나? |
| 6 | 통계분석 | 눈으로 본 차이가 통계적으로도 성립하나? |
| 7 | ML Pipeline | 그래서 예측할 수 있나? |
| 8 | 한계 | 이 결과를 어디까지 믿으면 되나? |

**근거**
자동 실행 결과에서 사람이 가장 먼저 확인해야 할 것은 분석 내용이 아니라
**"이번 실행이 정상인가"**다. 게이트가 하나라도 실패했다면 아래 내용을
읽을 이유가 없다. 그래서 품질 게이트를 앞에 둔다.

그다음은 **처리 → 관찰 → 검정 → 예측** 순이다. 차트를 보기 전에 통계
검정 결과를 먼저 읽으면 "그래서 분포가 어떻길래?"라는 의문이 남는다.
반대 순서면 차트에서 본 차이를 검정이 확인해 주는 흐름이 된다.

**바뀐 점**: 기존에는 "처리 근거"가 시각화보다 앞이라 근거 문장을 읽을 때
아직 그림을 못 본 상태였다. 데이터 준비 섹션 안으로 넣어 처리 흐름과 붙였다.

## 결정 R-3. 맨 앞에 개요를 넣는다

**결정**
분석 대상·목적·핵심 결과를 3~4줄로 요약해 맨 앞에 배치한다.

**근거**
발표가 없으므로 "이 리포트가 무엇인지" 말해 줄 사람이 없다.
지금 리포트는 `run_id` 표로 시작하는데, 처음 보는 사람에게 해시값은
아무 의미가 없다. **무엇을 분석했고 결론이 무엇인지**가 먼저 와야 한다.

**한계**
개요는 자동 생성이라 지표를 조합한 문장이다. 사람이 쓴 통찰만큼
매끄럽지 않지만, 매 실행 자동으로 갱신되는 이점이 더 크다.

## 결정 R-4. 한계를 한곳에 모은다

**결정**
각 단계가 `[한계]`로 시작하는 note를 내면 리포트 마지막에 모아 싣는다.

**근거**
현재 한계 문장은 각 단계의 "처리 근거" 안에 흩어져 있다.
- 결측: 카드결제 한정, partial 소스 제외
- 통계: 관측 독립성 위반, 사후 선택
- 모델: 무작위 분할, 하이퍼파라미터 미튜닝

읽는 사람이 "이 결과를 어디까지 믿어야 하나"를 판단하려면 이것들을
한눈에 봐야 한다. 흩어져 있으면 결국 아무도 종합하지 못한다.

**구현**: 단계는 지금처럼 `[한계]` 접두사가 붙은 note를 내기만 하면 된다.
리포트가 그것을 모아 별도 섹션으로 만든다. 단계 코드를 고칠 필요가 없다.

**한계**
접두사 규칙에 의존하므로 새 단계에서 `[한계]`를 빠뜨리면 조용히 누락된다.
표기 규칙을 리포트 모듈 상수로 두어 한 곳에서 관리한다.
