## 1. 공통 결정

### 결정 C-1. 전체 388만 행을 그대로 쓴다 (샘플링하지 않는다)

**결정** 모든 차트를 전체 데이터로 계산한다. 표본 추출을 하지 않는다.

**근거**
그릴 때 실제로 비싼 연산이 무엇인지 실측했다.

| 연산 | 대상 | 소요 |
|---|---|---:|
| 히스토그램 binning | 전체 388만 | **0.03초** |
| 피어슨 상관 | 전체 388만 × 4열 | **0.08초** |
| 스피어만 상관 | 전체 388만 × 4열 | **0.89초** |
| 스피어만 상관 | 50만 샘플 | 0.14초 |
| 시간대×요일 집계 | 168셀 | **0.13초** |

**전부 1초 미만이다.** 샘플링으로 아낄 시간이 0.75초뿐인데,
표본 추출은 "이 그림이 전체를 대표하는가"라는 의문을 새로 만든다.
얻는 것보다 잃는 것이 크다.

**반례 — 샘플링이 필요한 경우**
산점도(scatter)나 커널밀도추정(KDE), 바이올린 플롯은 **점 하나하나를
렌더링**하므로 388만 점에서 수십 초가 걸리거나 아예 멈춘다.
그래서 이번 차트는 전부 **집계 기반**(히스토그램·히트맵)으로만 구성했다.
집계는 데이터를 구간으로 묶으므로 행 수가 늘어도 렌더링 비용이 일정하다.

**한계**
차트 종류를 집계 기반으로 제한한 결과, 개별 관측의 산포를 보여주는
표현(산점도·바이올린)은 쓸 수 없다. 필요해지면 그때 샘플링 근거를 세운다.

### 결정 C-2. 폰트를 `AppleGothic`으로 고정한다

**결정** matplotlib `font.family = "AppleGothic"`, `axes.unicode_minus = False`.

**근거**
- 축 레이블·제목에 한글을 쓰는데, 기본 폰트로는 **모두 두부(□□□)로 깨진다.**
  레이블이 깨지면 **그림이 무엇을 말하는지 알 수 없다.**
- 설치된 한글 폰트를 조회해 `AppleGothic`, `Apple SD Gothic Neo`, `NanumGothic`이
  있음을 확인했고, 실제 렌더링으로 한글과 음수 부호가 정상 출력됨을 검증했다.
- `axes.unicode_minus = False`가 필요한 이유: matplotlib 기본값은 음수에
  유니코드 마이너스(U+2212)를 쓰는데, 한글 폰트에 이 글자가 없어 깨진다.

**반례**
설정하지 않으면 `이동거리 분포` → `□□□□ □□`가 되어 축이 무엇인지 읽을 수 없다.

**한계**
`AppleGothic`은 macOS 전용이다. 다른 OS에서 실행하면 경고와 함께 기본 폰트로
넘어간다. **설정 파일에 폰트 후보 목록을 두고 사용 가능한 것을 고르도록** 구현한다.

---

### 결정 C-3. Seaborn은 PNG, Plotly는 HTML + PNG 둘 다 만든다

**결정**
| 라이브러리 | 저장 | 리포트에서 |
|---|---|---|
| Seaborn | `.png` | 본문 임베드 |
| Plotly | `.html` **+** `.png` | PNG 임베드 + HTML 링크 |

**근거**
- 마크다운은 외부 HTML을 본문에 렌더링하지 못한다. **HTML만 저장하면
  `report.md`에는 링크만 남고 그림이 보이지 않는다.**
- 발표가 없어 리포트가 유일한 전달 수단이다. 클릭해야만 보이는 차트는
  "리포트만 읽고 이해 가능"이라는 조건을 깨뜨린다.
- 반대로 PNG만 만들면 **마우스오버로 값을 확인하는 기능을 쓸 수 없다.**
- PNG 변환에 `kaleido`가 필요하며 동작을 확인했다(plotly 6.9 + kaleido 1.3).

**한계**
PNG 변환은 별도 렌더링 엔진을 띄우므로 몇 초가 걸린다. 차트가 늘면
파이프라인 실행 시간에 영향을 준다. 현재 1개뿐이라 문제되지 않는다.

---

### 결정 C-4. 차트는 `run_id` 디렉터리에 격리한다

**결정** `outputs/runs/<run_id>/figures/` 아래에 저장한다.

**근거**
- 실행마다 데이터·설정이 다를 수 있는데 같은 경로에 덮어쓰면
  **과거 리포트가 현재 차트를 가리키게 된다.** 리포트와 그림이 어긋난다.
- `report.md`가 같은 디렉터리에 있으므로 상대경로 `figures/x.png`가 그대로 동작한다.

**구현 방식 — 단계는 파일을 쓰지 않는다**
기존 설계 원칙(계획서 §3-2)은 "분석 로직은 파일을 읽지도 쓰지도 않는다"였다.
차트는 파일이므로 이 원칙과 충돌한다. 다음처럼 푼다.

```python
# 단계는 '저장하는 방법'만 넘기고, 어디에 저장할지는 runner가 정한다
StepResult(df=df, metrics={...}, artifacts=[
    Artifact(name="distance.png", save=lambda p: fig.savefig(p), caption="...")
])
```

단계는 여전히 경로를 모르고, runner가 `run_id` 디렉터리를 결정한다.
테스트에서는 임시 경로를 넘겨 저장 동작만 검증할 수 있다.

## 2. 차트별 설계

### 대표 예시 1 — 수치형 분포 (Seaborn · 분포)

**목적** "평균을 대표값으로 써도 되는가"에 답한다.

**근거**

| 통계량 | 값 |
|---|---:|
| 평균 | 3.52 mile |
| 중앙값 | 1.93 mile |
| 95% 분위 | 12.60 |
| 99% 분위 | 19.45 |
| 최댓값 | 99.66 |

**평균이 중앙값의 1.8배**다. 소수의 장거리 운행이 평균을 끌어올린 결과이며,
"뉴욕 택시는 평균 3.5마일을 간다"는 서술은 절반 이상의 운행(중앙값 1.93)을
잘못 대표한다. 이 왜곡은 숫자만으로는 와닿지 않아 그림이 필요하다.

**표현 결정**
- 평균선·중앙값선을 **수직선으로 함께 표시** — 둘의 간격이 왜곡의 크기다
- x축을 **0~20마일로 제한**한다
  - 근거: 20마일 이하가 **99.2%**를 차지한다. 100마일까지 그리면
    막대가 왼쪽 끝에 뭉쳐 아무것도 안 보인다.
  - 잘라낸 0.8%는 **차트 안에 명시**한다. 그래야 정직한 그림이 된다.

**한계**
꼬리를 잘랐으므로 극단값의 존재감이 실제보다 작아 보인다.
분위수 정보를 캡션에 함께 적어 보완한다.

---

### 대표 예시 2 — 시간대 × 요일 운행량 (Plotly · 인터랙티브)

**목적** 수요가 언제 몰리는지 두 축으로 동시에 본다.

**근거 — 왜 인터랙티브가 필요한가**
168개 셀(24시간 × 7요일)의 값을 정적 이미지에 모두 표기하면 읽을 수 없다.
Plotly는 **셀에 마우스를 올렸을 때만 정확한 값을 보여주므로**,
전체 패턴은 색으로 보고 개별 값은 필요할 때 확인할 수 있다.
인터랙티브가 장식이 아니라 정보 밀도 문제를 푸는 수단이다.

**근거 — 왜 이 축 조합인가**
기존 EDA에서 확인한 두 축이다. 시간대별로는 18시가 최다(252,341건),
4시가 최소(30,949건)이고, 결측 편향도 시간대에 따라 16.3%~50.9%로 갈렸다.
**같은 축으로 수요를 보면 결측 편향이 수요 패턴과 겹치는지 판단할 수 있다.**

**표현 결정**
- 집계 후 그린다(168셀). 원자료를 넘기면 브라우저가 멈춘다.
- 색상 스케일은 순차형(단일 색조)을 쓴다. 운행량은 방향성 없는 양적 변수이므로
  발산형(빨강-파랑)은 중간값에 의미가 있다는 잘못된 인상을 준다.

**한계**
운행량은 절대 건수라 요일별 일수 차이(5월에 금·토가 5번, 나머지는 4번)의
영향을 받는다. 캡션에 명시한다.

## 3. 설정 파일에 반영할 값

```toml
[visualize]
font_candidates = ["AppleGothic", "Apple SD Gothic Neo", "NanumGothic"]  # C-2
dpi = 120                      # 리포트 임베드용. 300은 파일이 커지고 화면에선 차이 없음
figsize = [10, 6]
distance_xlim = 20             # 차트1: 99.2% 포함 (결정 근거 §차트1)
```
