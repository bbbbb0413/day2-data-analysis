## 3. 작업 원칙

### 3-1. 모든 데이터 처리 결정에는 근거를 남긴다

이 과제의 핵심 요구다. 다음 형식을 지킨다.

```
결정 : 무엇을 어떻게 처리했는가
근거 : 이 데이터에서 관측된 사실 (숫자 포함)
반례 : 그렇게 하지 않았을 때 무슨 일이 생기는가 (실측)
한계 : 이 판단이 틀릴 수 있는 조건
```

`결측치_중복_처리기준.md`가 이미 이 형식을 따르고 있다. 신규 단계도 동일하게 쓴다.

### 3-2. 자동화 파이프라인 안에서 동작해야 한다

새 기능을 별도 스크립트로 만들지 않는다. 기존 계약을 그대로 따른다.

```python
def 단계(df: DataFrame, cfg: Config) -> StepResult:
    return StepResult(df=..., metrics={...}, notes=["근거 문장"])
```

- 임계값·설정은 **코드가 아니라 `config/pipeline.toml`**에
- 지표는 `metrics`로 반환 → `metrics.json`에 자동 기록
- 근거 문장은 `notes`로 반환 → `report.md`에 자동 게재
- 기대값은 **품질 게이트**에 등록 → 어긋나면 종료 코드 1

### 3-3. 재현 가능해야 한다

- 모든 난수에 `random_state` 고정, 설정 파일에 명시
- 샘플링·분할 기준을 설정으로 노출
- 산출물은 `run_id` 디렉터리에 격리

## 4. 계획의 전제 — 이미 확인한 사실

계획을 세우기 전에 데이터를 확인했다. **아래 사실이 STEP 1~4의 설계를 결정한다.**

### 4-1. 팁은 결제수단에 완전히 종속된다 ★ 가장 중요

| `payment_type` | 건수 | 팁=0 비율 | 평균 팁 |
|---|---:|---:|---:|
| 1 (카드) | 2,660,701 | 9.8% | 4.273 |
| 2 (현금) | 350,545 | **100.0%** | 0.000 |
| 3 (무료) | 5,967 | **100.0%** | 0.002 |
| 4 (분쟁) | 4,246 | **100.0%** | 0.000 |
| NaN (partial 소스) | 863,163 | 90.8% | 0.458 |

**현금 결제는 팁이 구조적으로 0으로 기록된다.** 실제로 팁을 안 준 게 아니라
시스템이 기록하지 않는다. 팁 관련 분석·모델링을 전체 데이터로 하면
"결제수단 맞히기"를 하는 셈이 된다.

→ **팁을 다루는 모든 분석은 `payment_type == 1` 한정으로 수행한다.**

### 4-2. 표본이 커서 t-test의 p-value가 무의미해진다 ★

주말 vs 평일 평균 요금을 예로 계산했다.

| 항목 | 값 |
|---|---:|
| 주말 평균 요금 | 20.932 |
| 평일 평균 요금 | 21.696 |
| 차이 | −0.764 |
| 표준편차 | 17.39 |
| **Cohen's d** | **0.0439** |

n≈388만에서는 이 정도 차이도 **p < 0.001**이 나온다. 통계적 유의성과
실질적 중요성은 다르다. 효과크기 0.044는 관례상 "무시 가능"에 해당한다.

→ **t-test 결과에 반드시 효과크기(Cohen's d)와 신뢰구간을 병기하고,
"유의하지만 실질적으로는 작다"를 해석에 명시한다.** p-value만 보고
"차이가 있다"고 쓰면 틀린 해석이다.

### 4-3. `total_amount`는 `tip_amount`를 포함한다 — 데이터 누수

총액은 팁을 포함한 합계다. 팁을 예측하면서 `total_amount`를 피처로 넣으면
정답을 입력에 포함시키는 것과 같다.

→ **타깃과 산술적으로 연결된 컬럼은 피처에서 전부 제외한다.**

### 4-4. 이진 타깃 후보의 클래스 균형

| 후보 | 양성 비율 | 판단 |
|---|---:|---|
| 고액팁 (팁/요금 ≥ 20%) | 50.92% | **균형 우수** |
| 팁 있음 (>0) | 63.80% | 양호하나 §4-1 문제 직결 |
| 장거리 (≥5 mile) | 19.67% | 불균형 |
| 공항 관련 | 6.31% | 심한 불균형 |
| 심야 (22~05시) | 19.49% | 불균형 |

→ 클래스 균형이 좋으면 정확도가 의미를 갖고 F1도 안정적이다.
**"고액팁 여부"가 유력하나, `payment_type==1` 한정으로 재계산해 STEP 1에서 확정한다.**

### STEP 1. 분석 설계 확정 ★ 가장 중요

| 항목 | 내용 |
|---|---|
| **목적** | 무엇을 검정하고 무엇을 예측할지 **데이터 근거로** 결정 |
| **배점 연결** | B3~B7 (40점)의 전제 |
| **산출물** | `docs/01_분석설계_근거.md` |
| **구현** | 없음 (설계만) |

**결정할 것**

1. **t-test 가설 2개 이상 확정**
   - 후보 ①: 카드결제 한정, 공항 운행 vs 비공항 운행의 **팁 비율**
   - 후보 ②: 주말 vs 평일 **운행 거리**
   - 후보 ③: `record_source` full vs partial의 **평균 요금**
     (§4-1에서 확인한 소스 차이가 요금에도 나타나는지)
   - 선정 기준: (a) 두 집단이 **명확히 정의**되고, (b) 실무적으로 **의미 있는
     질문**이며, (c) 효과크기가 무시 가능하지 않을 가능성이 있는 것

2. **t-test 전제 검토** — 여기가 근거 문서의 핵심
   - `ttest_ind`의 기본값은 **등분산 가정(Student's t)**이다.
     두 집단의 분산이 다르면 `equal_var=False`(Welch)를 써야 한다.
     → **분산비를 실측해 어느 쪽을 쓸지 근거와 함께 결정**
   - 정규성: n이 크면 중심극한정리로 평균의 분포는 정규에 가까워지므로
     원자료의 비정규성은 큰 문제가 아니다. 다만 **극단 왜도**는 확인한다.
   - 독립성: 같은 차량의 연속 운행은 독립이 아닐 수 있다 → 한계로 명시

3. **ML 문제 정의 확정**
   - 문제 유형: **이진 분류** (채점 기준이 "정확도·F1"을 명시 → 분류)
   - 타깃 후보: 고액팁 여부 (§4-4)
   - 대상 범위: `payment_type == 1` 한정 (§4-1 근거)
   - **피처에서 제외할 컬럼과 그 이유** (§4-3 누수 방지)
   - 학습 표본 크기와 샘플링 방식 (§ 아래)

4. **샘플링 여부 결정**
   - 266만 행 전체 학습은 시간·메모리 부담
   - 층화 샘플링으로 줄일지, 전체를 쓸지 **실측 후 결정**
   - 줄인다면 **타깃 비율을 보존하는 층화 추출**이어야 한다는 근거 명시

**검증**: 문서에 각 결정마다 `결정/근거/반례/한계` 4항목이 채워졌는가

- 발표가 없어 리포트가 유일한 전달 수단이다. 링크를 클릭해야만 보이는 차트는

- 반대로 PNG만 저장하면 **인터랙티브 요건(A6)을 증명할 수 없다.**
- → 둘 다 만든다. HTML은 요건 증빙 + 실제 탐색용, PNG는 리포트 본문용.
- PNG 변환에는 `kaleido`가 필요하다(설치 확인 완료, plotly 6.9 + kaleido 1.3).

**필수 준수 사항**
- **제목·축 레이블 반드시 포함** (채점 기준 명시)
- 한글 폰트 깨짐 방지 처리 (macOS `AppleGothic`) — 깨지면 레이블 판정 불가
- 차트 파일은 `run_id` 디렉터리 안에 두어 실행마다 격리
  (리포트의 상대경로 `figures/x.png`가 그대로 동작한다)
- 388만 점 산점도는 렌더링 불가 → **집계 후 그리거나 샘플링**, 그 근거 문서화

**파이프라인 통합**
- `mutates=False` (DataFrame 변경 없음)
- 차트 경로를 `metrics`에 기록 → `report.md`에서 참조

**검증**: 파일 생성 확인 + 제목·축 레이블 존재 확인

### STEP 3. 통계분석 단계 구현

| 항목 | 내용 |
|---|---|
| **목적** | 기술통계·상관계수·t-test와 **해석** |
| **배점 연결** | B1~B4 |
| **산출물** | `taxi_pipeline/steps/statistics.py`, `docs/03_통계분석_근거.md` |

**구현 내용**

1. **기술통계** — 평균·표준편차·분위수를 **명시적으로** 출력
   (현재 `profile`은 표준편차를 안 내보내므로 보강)
2. **상관계수** — 피어슨 + **스피어만 병기**
   - 근거: 거리·요금이 심하게 치우쳐 있어(§STEP2 차트1) 피어슨은
     극단값에 끌린다. 순위 기반 스피어만을 함께 봐야 한다.
3. **t-test** — `scipy.stats.ttest_ind` 사용 (요건 지정)
   - STEP 1에서 확정한 가설 2개 이상
   - `equal_var` 선택 근거 명시
4. **p-value 해석** — 요건 B4
   - **반드시 포함**: 효과크기(Cohen's d), 신뢰구간, 표본 크기
   - "p < 0.05이므로 유의하다"로 끝내지 않는다.
     §4-2에서 확인했듯 n=388만에서는 거의 모든 검정이 유의해진다.
   - 해석 문장을 `notes`로 반환 → `report.md`에 자동 게재

**검증**: `ttest_ind` 호출 확인, 해석 문장에 효과크기 포함 확인

### STEP 4. ML Pipeline 단계 구현 ★ 배점 최대

| 항목 | 내용 |
|---|---|
| **목적** | 전처리+모델을 `Pipeline` 객체로 구성, 평가, 저장 |
| **배점 연결** | B5~B7 |
| **산출물** | `taxi_pipeline/steps/model.py`, `docs/04_ML파이프라인_근거.md` |
| **모델 파일** | `outputs/runs/<run_id>/model.joblib` |

**Pipeline 구성 (요건: `sklearn.pipeline.Pipeline`)**

```
ColumnTransformer
├─ 수치형 : SimpleImputer(median) → StandardScaler
└─ 범주형 : SimpleImputer(most_frequent) → OneHotEncoder
        ↓
    분류 모델
```

**각 선택에 필요한 근거 (문서에 반드시 기술)**

| 결정 | 근거로 답해야 할 질문 |
|---|---|
| 타깃 정의 | 왜 이 임계값인가? 클래스 비율은? |
| 대상 범위 | 왜 `payment_type==1`만인가? (§4-1) |
| 피처 선택 | 왜 이 컬럼들인가? **누수 컬럼을 왜 뺐는가?** (§4-3) |
| 결측 대체 | Pipeline 안의 `SimpleImputer`는 §2의 "채우지 말라"와 모순 아닌가? |
| 스케일링 | 왜 필요한가? 트리 모델이면 불필요한데 왜 넣었나? |
| 모델 선택 | 왜 이 모델인가? 해석 가능성 vs 성능 |
| 학습/평가 분할 | 왜 이 비율인가? **시간 순 분할이 필요한가?** |
| 평가 지표 | 정확도만으로 충분한가? F1을 함께 보는 이유 |

> **주목**: "결측을 채우지 말라"(문서 §2)와 "Pipeline에 Imputer를 넣는다"는
> 겉보기에 모순이다. 실제로는 **분석용 데이터셋(결측 보존)**과
> **모델 입력(대체 필요)**의 목적이 다르기 때문이다.
> 이 구분을 근거 문서에 명확히 써야 한다. 채점자가 볼 만한 지점이다.

**필수 준수**
- `joblib.dump`로 저장 (요건 지정)
- 평가 지표: accuracy, F1, precision, recall, ROC-AUC
- `random_state` 고정

**검증**: 모델 파일 생성 + 재로딩 후 예측 재현 확인

## 6. 파이프라인 통합 설계

신규 3개 단계를 기존 목록에 추가한다.

```python
PIPELINE = [
    Step("analyze_missing",  ..., mutates=False),
    Step("prepare_missing",  ...),
    Step("deduplicate",      ...),
    Step("filter_outliers",  ...),
    Step("profile",          ..., mutates=False),
    Step("visualize",        ..., mutates=False),   # STEP 2 신규
    Step("statistics",       ..., mutates=False),   # STEP 3 신규
    Step("model",            ..., mutates=False),   # STEP 4 신규
]
```

**순서 근거**: 셋 다 정제 완료 데이터를 입력으로 받아야 하므로 `filter_outliers`
뒤에 온다. 서로 간에는 의존성이 없어 순서를 바꿔도 결과가 같다.

**설정 추가 예정 (`config/pipeline.toml`)**

```toml
[visualize]      # 차트 크기·DPI·샘플 수
[statistics]     # 유의수준, 검정 대상 정의
[model]          # 타깃 임계값, 테스트 비율, random_state, 모델 하이퍼파라미터
```

**품질 게이트 추가 예정**

| 항목 | 이유 |
|---|---|
| 차트 파일 개수 | 생성 실패를 조용히 넘기지 않기 위해 |
| 모델 F1 하한 | 성능이 무너지면 실패로 처리 |
| 학습 표본 수 하한 | 필터를 잘못 걸어 데이터가 말라붙는 사고 방지 |
